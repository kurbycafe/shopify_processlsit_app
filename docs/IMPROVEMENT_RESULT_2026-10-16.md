## 운영 반영 전 필요한 단계

1. 추가 스키마를 검토하고 기존 배포 준비 경로로 적용한다. `CustomerRequest`, `CustomerNotificationPreference`, nullable `InspectionItem.orderLineId`가 추가된다. 기존 테이블·행을 삭제하지 않는다.
2. 현재 저장소에 이전 Prisma 마이그레이션 baseline이 없으므로, 운영 DB에 `migrate reset`이나 무검토 `migrate deploy`를 실행하지 않는다. 기존 Vercel 준비 스크립트와 추가 SQL의 적용 절차는 `docs/customer-requests.md`를 참고한다.
3. 배포 후 실제 고객 두 계정으로 본인/타인 주문, 반품 접수, 알림 설정, 직원 인쇄 수정 권한을 확인한다. 실제 Shopify·Odoo·메일 계정 흐름은 이번 모의 테스트로 대체하지 않는다.
4. 만료 없는 이전 인쇄 링크는 새로 생성한다. 재입고 알림 API 취소에는 고객 로그인이 필요하며 공개 위젯에서는 고객센터 안내를 제공한다.

## 의도적으로 남긴 기능 한계

- B2B·반품은 관리자 검토 요청을 저장한다. 자동 메일, Shopify 반품 승인·환불 실행은 포함하지 않는다.
- 모바일 반품 화면의 이후 관리자 상태 자동 동기화·고객용 서버 이력 조회 API는 추가하지 않았다.
- 알림 설정 저장과 실제 푸시 기기 등록은 별도 단계다. 실제 제공자 토큰 저장만으로 푸시 전달 성공을 보장하지 않으며, 제공자 설정·실기기 수신 확인이 필요하다. Shopify 마케팅 수신 동의 변경은 실행하지 않는다.
- 과거 월말 재고는 기존 저장 자료가 없어 제공하지 않는다. 현재 재고의 날짜만 바꿔 제공하지 않는다.
- 외부 제공자 접수 직후 서버 중단 또는 DB 전체 장애로 완료/확인 필요 상태를 모두 저장하지 못하면 만료 작업 재시도 시 중복될 가능성이 남는다. 제공자 측 멱등성 키·영속 outbox는 추가 작업이다. 확인 절차는 `docs/notification-reconciliation.md`에 기록했다.
- 실제 고객 로그인, 운영 송장·메일·입고 흐름, 모바일 실기기 및 새 APK/iOS 배포는 검증하지 않았다.
